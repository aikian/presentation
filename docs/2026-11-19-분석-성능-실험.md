# 영상 분석 성능 실험 (2026-11-19)

## 1. 배경

최종 평가 피드백 7번: 서버 사양이 낮으면 영상 길이에 따라 수분씩 기다려야 하고, 동시 접속 2~3명만 몰려도 불편할 것이다. 연산량을 줄일 방법이 있는가.

운영 서버(개인 NAS)는 인텔 저전력 4코어, RAM 약 11GB, 스왑 4GB다. 점검 시점에 스왑이 100% 차 있었다. 코드를 보니 영상 분석이 다음 구조였다.

- 영상을 세 번 디코딩한다. 얼굴·자세용 2초 간격, 손용 0.5초 간격, 길이 측정용.
- 뽑은 프레임을 원본 해상도 그대로 전부 리스트에 쌓은 뒤 얼굴, 자세, 손 모델을 차례로 돌린다.
- 슬라이드 변환(LibreOffice, 최대 2분)이 async 함수 안에서 동기로 돌아 그동안 서버 전체 요청이 멈춘다.

프레임을 쌓는 구조는 영상이 길고 해상도가 높을수록 메모리가 비례해서 늘어난다. 스왑이 꽉 찬 서버에서는 CPU보다 메모리가 병목일 가능성이 컸다. 그래서 바꾸기 전에 측정했다.

## 2. 바꾼 것

1. 디코딩 1회. 한 번 읽으면서 2초·0.5초 간격 프레임을 동시에 뽑고, 길이 측정에 디코딩을 다시 하지 않는다.
2. 스트리밍 처리. 프레임을 쌓지 않고 한 프레임씩 얼굴, 자세, 손 모델을 바로 돌린다. 세 모델은 static_image_mode라 프레임 간 상태가 없어 결과가 같다. 시선 이탈 문제 장면은 영상 전체 중앙값을 안 뒤에 고르므로 얼굴 간격 프레임의 JPEG 바이트만 남긴다.
3. 프레임 축소 옵션 MAX_FRAME_SIDE. 긴 변을 지정 크기로 줄여 모델에 넣는다. 기본값 0(원본 유지)이고 운영에서는 켜지 않았다. 이유는 4절.
4. 슬라이드 변환을 스레드풀로 분리.
5. 분석 대기 순번을 상태 API와 진행 화면에 표시.

## 3. 방법

- 스크립트: `backend/scripts/compare_frame_side.py`. 설정마다 별도 프로세스로 돌려 최대 메모리(RSS)가 섞이지 않게 했다.
- 측정 머신: 개발용 맥북(Apple Silicon). 운영 NAS보다 빠르므로 절대값이 아니라 구조 간 비율로 읽어야 한다.
- 음성 분석은 꺼 둠(ENABLE_AUDIO_ANALYSIS=false). 영상 처리 구조만 비교하기 위해서다.
- 옛 구조는 변경 전 커밋을 별도 작업 폴더에 받아 같은 스크립트로 돌렸다.
- 영상 3개. 모두 로컬 디스크에 복사해 두고 돌렸다.

| 이름 | 해상도 | 길이 | 성격 |
|---|---|---|---|
| talk720p_14min | 1280x720 30fps | 14분 6초 | 롤모델 연사 무대 강연. 얼굴 검출률 96% |
| rec1080p_4.5min | 1920x1080 30fps | 4분 29초 | 발표자가 멀리 작게 잡힌 녹화. 얼굴 검출률 9% |
| selfie1080x1920_32s | 1080x1920 60fps | 32초 | 세로 셀카 클립. 얼굴 검출률 18% |

## 4. 결과

### 4.1 옛 구조 대 새 구조 (원본 해상도, 같은 시각에 연달아 측정)

| 영상 | 옛 시간 | 새 시간 | 옛 최대 메모리 | 새 최대 메모리 |
|---|---|---|---|---|
| talk720p_14min | 164.0초 | 100.3초 | 2,717 MB | 477 MB |
| rec1080p_4.5min | 119.4초 | 64.1초 | 4,340 MB | 542 MB |
| selfie1080x1920_32s | 17.0초 | 9.0초 | 852 MB | 518 MB |

- 시간은 1.6~1.9배 빨라졌다.
- 메모리는 영상에 비례하던 것이 0.5GB 안에서 고정됐다. 1080p 4.5분 영상에서 4.3GB가 0.5GB로 줄었다.
- 지표(얼굴 검출률, 시선 이탈률, 어깨 기울기, 분당 제스처, 제스처 유효 비율, 미소 비율)와 점수는 세 영상 모두 소수점까지 같았다.

옛 구조의 단계별 시간을 보면 디코딩이 전체의 56~87%였다(talk720p 92.7초/164초, rec1080p 103.6초/119초). 디코딩 두 번과 메모리 압박이 겹친 결과다.

### 4.2 프레임 축소(MAX_FRAME_SIDE)의 점수 영향

새 구조에서 원본과 960px, 640px를 비교했다. 롤모델 영상 2편(720p 14분)과 짧은 영상 4개를 썼다.

| 영상 | 960px 점수 변화 | 640px 점수 변화 |
|---|---|---|
| 롤모델 A (720p, 얼굴 96%) | 전 항목 0 | 시선 -2, 제스처 -7 |
| 롤모델 B (720p, 얼굴 88%) | 제스처 +1 | 제스처 +8 |
| rec1080p_4.5min (얼굴 9%) | 시선 -33 | 시선 -27 |
| selfie 32초 (얼굴 18%) | 자세 -14 | 자세 -14 |
| selfie 13초 (얼굴 29%) | 0 | 시선 -100, 제스처 측정 불가 |

- 얼굴이 크게 잡히는 정상 발표 영상은 960px에서 점수가 같고 640px부터 제스처가 흔들린다.
- 얼굴이 작게 잡히는 영상은 960px에서도 검출 결과가 뒤집혀 점수가 크게 움직인다. 프레임이 적은 짧은 영상은 한 프레임만 바뀌어도 비율이 크게 변한다.
- 720p 영상에서는 축소해도 시간이 거의 줄지 않았다(100.3초 대 100.1초). 디코딩은 해상도와 무관하게 전부 해야 하고, 맥북에서는 모델 추론이 이미 빨라서다.

결론: 축소는 점수를 바꿀 수 있고 시간 이득은 작다. 기본값을 0으로 두고 운영에 켜지 않는다. 얼굴 크기에 따라 축소 비율을 정하는 방식(얼굴 상자가 일정 픽셀 이상일 때만 축소)을 검토한 뒤 적용한다.

## 5. 서버 사양 계산

측정값으로 작업 1건의 자원을 잡는다.

- 메모리: 새 구조 영상 처리 0.5GB. 음성 분석(faster-whisper small int8, librosa)을 켜면 모델과 버퍼로 약 1GB가 더 든다(추정, 별도 측정 필요). 작업 1건 약 1.5GB. 옛 구조는 영상만 2.7~4.3GB여서 작업 1건 4~5.5GB였다.
- CPU: 맥북에서 14분 720p 영상이 100초, 영상 길이의 12%. 저전력 인텔 4코어는 코어당 성능이 3~4배 낮다고 보면 300~400초, 영상 길이의 40~50%다. 동시 2건이면 코어를 나눠 쓰므로 더 길어진다.

현재 NAS(RAM 11GB, 스왑 4GB)에 옛 구조로 분석 스레드 2개를 두면 분석만 8~11GB를 쓴다. OS, Docker, 프론트, 백엔드 상주 메모리를 더하면 RAM을 넘어 스왑으로 밀린다. 스왑이 100% 찬 상태가 이것을 보여준다. 새 구조에서는 2건 동시에 3GB 안이다.

권장 사양(새 구조 기준):

| 동시 분석 | vCPU | RAM | 비고 |
|---|---|---|---|
| 2건 | 4 | 8GB | 지금 NAS 코어 수와 같지만 스왑 없이 돈다 |
| 4건 | 8 | 16GB | 수업 한 반이 같은 시간에 올리는 수준 |

분석 작업은 웹 서버와 분리해 별도 워커 프로세스와 큐로 돌리고, 워커 수를 코어 수에 맞춰 조절하는 구조가 맞다. 그래야 서버 사양을 올릴 때 워커 수만 바꾸면 된다.

프론트엔드는 정적 파일이라 Vercel 무료 플랜으로 분리하면 백엔드 서버 부담이 줄고 HTTPS와 CDN이 따라온다. 백엔드(ffmpeg, LibreOffice, MediaPipe, Whisper)는 몇 분씩 도는 작업이라 서버리스에는 올릴 수 없고 위 표의 일반 서버가 필요하다.

## 7. 적용 상태

- 디코딩 1회, 스트리밍 처리, 슬라이드 변환 분리, 대기 순번: 코드 반영. 결과값이 바뀌지 않으므로 머지 후 배포에 포함한다.
- 프레임 축소: 코드만 넣고 기본값 0으로 꺼 둠.
- 다음 단계: 배포 후 운영 서버의 메모리·스왑 추이 확인, 음성 분석 포함 메모리 측정, 워커 큐 분리, 얼굴 크기 기반 축소.

## 8. 재현 방법

```
cd backend
PYTHONPATH=. python scripts/compare_frame_side.py 영상.mp4 --sides 0 960 640 --out 결과.json
```

`.env`에서 `ENABLE_AUDIO_ANALYSIS=false`로 두면 영상 처리만 측정된다. 결과 JSON에 설정별 총 시간, 최대 메모리(MB), 지표, 점수가 남는다.
